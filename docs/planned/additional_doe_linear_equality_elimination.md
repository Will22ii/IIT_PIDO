# additional DOE의 pre Type 2 등식 — 변수 소거

| | |
|---|---|
| 상태 | **설계만. 미구현. 우선순위 낮음(보류)** |
| 대상 | pre scope, Type 2(eps 공란), **선형** 등식 |
| 핵심 | 등식을 풀어 변수를 소거하면 additional DOE를 **수정 없이** 쓸 수 있다 |

Type 1/Type 2 구분은 [`doe_pre_equality_projection.md`](doe_pre_equality_projection.md)를 먼저 읽는다.

---

## 1. 문제

plain DOE는 Type 2 pre 등식을 투영으로 푼다(구현 완료). additional DOE는 못 푼다.

`additional_orchestrator.py:370`은 Type 1/2를 구분하지 않는다. `type == "=="`이면 전부
한 덩어리로 세어 후보를 최대 8배로 늘리고 rejection에 넣는다(로그: `policy=eps_band_rejection`).

Type 2는 이 방식으로 원리적으로 못 푼다. 알고리즘이 부족해서가 아니라
**무작위 점이 정확 등식을 맞힐 확률이 0**이기 때문이다. 후보를 8배가 아니라 8000배로 늘려도 0이다.

## 2. 투영을 그대로 얹으면 안 되는 이유

additional DOE는 **정의역이 박스**라는 전제 위에 지어져 있다. Type 2 등식이 들어오면
정의역이 박스를 가로지르는 얇은 면이 되어 전제가 깨진다.

| 장치 | 등식이 있는 x 공간 |
|---|---|
| 통과율 `constraint_rate_hat` | 0 — 무의미 |
| margin | 항상 0 근처 |
| dedup 반경 `√p` | 실제 자유도보다 과대 |
| N/p 게이트 | p 기준이라 과잉 요구 |
| 코너 샘플링 | 면 밖 → 전부 버려짐 |

투영만 얹으면 통과율이 항상 100%가 되어 Gate 판정이 전부 무의미해진다.

**해법은 additional을 고치는 것이 아니라 깨진 전제를 되돌리는 것이다.**
자유도만큼의 좌표에서 보면 그 면은 다시 박스다.

## 3. 결론 — 변수 소거를 택한다

축소 방법은 둘이다. 검토 결과 **치환(변수 소거)**이 낫다.

```
치환   l4 = l1+l2-l3, 자유변수 l1,l2,l3 를 [0,10]^3 에서 샘플
       통과율 66.7%

영공간 x = x_p + Z·u, LP 최소 외접박스에서 샘플
       통과율 56.2%
```

(예제: `l1+l2 == l3+l4`, 전 변수 `[0,10]`, 20만 점)

둘 다 **같은 3차원 다면체**를 표현한다. 차이는 감싸는 박스가 얼마나 꽉 끼느냐뿐이다.
영공간은 좌표축을 회전시키므로 다면체가 박스를 비스듬히 가로질러 외접박스가 헐거워진다.

### 3.1 소거 변수 선택은 자동으로 해결된다

영공간을 검토했던 이유는 "치환은 소거 변수를 골라야 하고 특이할 수 있다"였다.
등식 2개(`l1+l2-l3-l4=0`, `l1-l3=0`)에서 후보 6개 중 2개가 실제로 불가능하다.

```
(0,1) 가능   (0,2) 불가(특이)   (0,3) 가능
(1,2) 가능   (1,3) 불가(특이)   (2,3) 가능
```

**열 피벗팅 QR이 잘 조건화된 조합을 자동으로 집는다.** 사람이 고를 필요가 없다.

과거 재매개화를 기각한 근거(가지 모호성)는 **비선형** 식을 sympy로 풀 때의 문제다.
선형 등식에는 해당하지 않는다 — 해가 유일하다.

### 3.2 결정적 이유는 변수 이름 보존

```
영공간   __u0 __u1 __u2 | d1 d2 ...     l1~l4 전부 익명
치환     l1 l2 l3       | d1 d2 ...     l4만 소거, 나머지 그대로
```

| | 영공간 | 치환 |
|---|---|---|
| Modeler FS | l1~l4 중요도 소실 | **l1,l2,l3 중요도 그대로** |
| Explorer bounds | 유저가 못 읽는 박스 | **원래 변수 범위** |
| debug 로그 | `__u0=3.2` | **`l1=3.2`** |
| 유저 보고 | 전 구간 복원 필요 | l4만 계산해 붙임 |

영공간을 택하면 **dummy가 real과 섞여 FS 검증이 무너진다.**
등식에 등장하는 변수만 변환하는 보완이 필요하지만, 치환은 그 문제가 애초에 없다.

## 4. 동작

```
유저 입력   변수 l1 l2 l3 l4 d1 d2 ...   +   등식 l1+l2 == l3+l4

① 등식이 선형인지 판정 (여러 점에서 야코비안이 상수인지)
② 피벗팅 QR로 소거 변수 자동 선택        → l4
③ l4 = l1 + l2 - l3 유도
④ 문제 재작성
     변수   l1 l2 l3 d1 d2 ...            (l4 제거)
     제약   등식 삭제
            l4의 원래 범위가 새 부등식으로   0 <= l1+l2-l3 <= 10
            l4를 쓰던 다른 제약은 l4 자리에 (l1+l2-l3) 문자열 치환
     평가   CAE 호출 직전에 l4 계산해 끼워넣음
⑤ 결과 보고 시 l4 값을 계산해 붙임
```

제약 재작성은 **문자열 치환**이므로 부등식이 비선형이어도 된다.
선형이어야 하는 것은 등식뿐이다.

**additional DOE는 한 줄도 바뀌지 않는다.** 등식이 사라지고 평범한 부등식만 남으므로
통과율·margin·Gate1/2·N/p·코너 샘플링이 전부 정상 작동한다.
조기 종료(`min_additional_rounds` 해제 후)도 이때 비로소 의미를 갖는다 —
x 공간에서는 통과율 0이라 Gate까지 도달하지 못한다.

## 6. 조용히 깨지는 곳

`evaluate_func`을 registry에서 **다시 가져오는** 경로가 둘 있다.

```
DOE/run_DOE.py:199-202              cae_output에 callable 없으면 재획득
Optimizer/executor/evaluation_core.py:221   조건 없이 재획득
```

CAE 함수는 positional unpack이다(`cantilever_beam.py:63`: `H, h1, b1, b2, dum1..dum5 = x`).
축소 좌표를 원 좌표인 척 그대로 받아먹어 **에러 없이 잘못된 값을 평가한다.**
Optimizer는 조건이 없으므로 반드시 발동한다.

두 지점은 변환의 존재를 알아야 한다. `CAE_model/`은 건드리지 않는다(제약 1) —
registry 반환값을 감싸는 것뿐이다.

## 7. known optimum

CAE metadata에 없다. `config_io.py:305-308`이 CAE 경로로 새지 않도록 제거하고,
`run_pipelines.py:449,463,1858,1893`에서 Explorer/Optimizer에 직접 주입한다.
**벤치마크 채점 경로가 CAE metadata를 우회한다.**

변환 자체는 가능하다. 정규직교 기저를 쓰면 역변환이 전치 하나다.

```
면 위 (3,4,5,2)   등식잔차 +0.000   왕복오차 0.00e+00
면 위 (1,9,6,4)   등식잔차 +0.000   왕복오차 8.9e-16
면 밖 (3,4,5,9)   등식잔차 -7.000   왕복오차 1.75e+00   ← 복원 실패
```

**왕복오차가 그대로 검사기가 된다.** known optimum이 등식을 어기면 복원되지 않는다.
이는 정답이 제약 밖에 있다는 뜻이므로 — 문제 정의가 모순이므로 — 조용히 넘기지 말고 에러로 잡는다.

같은 논리가 debug 로그에도 적용된다. 역변환 한 번이면 사람이 읽을 좌표가 나온다.

## 8. 남는 한계

- **비선형 등식은 불가.** 굽은 면에는 전역 좌표계가 없다. 수학적 장애물이지 구현 부족이 아니다.
  비선형 Type 2는 plain DOE의 투영으로 보낸다
- **Explorer가 고른 박스가 유도 변수의 범위를 벗어날 수 있다.**
  `0 <= l1+l2-l3 <= 10`이 부등식으로 남아 Optimizer는 그 안에서 탐색하지만,
  Explorer bounds 자체가 이를 보장하지는 않는다. 축소 방식과 무관한 공통 문제
- **검증 수단이 없다.** 벤치마크 4문제에 Type 2 등식이 없다.
  이 설계를 확인하려면 등식 있는 벤치마크와 7절의 known optimum 변환이 함께 필요하다.
  **구현보다 검증이 더 큰 일일 수 있다**

## 9. 미결정

- 유저가 준 baseline이 등식을 어길 때: 투영할지, 에러를 낼지
- 소거 변수를 유저에게 노출할지 (Explorer bounds에 l4를 유도값으로 붙일지)
- 자유도 0(등식 수 = 변수 수)일 때의 처리 — 현재는 에러로 가정
